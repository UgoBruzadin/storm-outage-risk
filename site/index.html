The question

Utilities stage repair crews before severe weather. To do that well they need to know not only when storms will cause outages, but where — and the same storm takes out 2% of one county and 40% of the next.

This project predicts, for every county and every 6-hour block, whether at least 1%, 5% or 10% of customers lose power, from storm ingredients (wind, gusts, wind shear, instability, rain, ice) and from what each place is like: tree canopy, housing age, density, and its own outage history. It builds on the weathernext-outage-forecasting approach and changes the parts that matter for an honest answer: place features, splits by time and by county instead of random days, and scoring new outages separately from ongoing ones.

What I found

Outages persist: a county that is out now will likely be out in six hours. A model can look accurate by learning only that. The useful part is the onset — a block whose previous six hours were calm — so every result below is scored on new outages. PR-AUC, where a model with no skill scores the event rate.

  • Weather predicts new outages 10–30× better than chance, and every feature group adds to it on both splits.
  • On new outages the model is a weather model. Its top features are surface wind, wind shear × instability, and wind × rain. Scored on all blocks instead, the previous block's outage outweighs everything else fifteenfold — that is persistence, not prediction.
  • Large outages are the most predictable relative to their rarity. Of the 1% of calm county-blocks the model ranks riskiest, about 1 in 8 become a ≥ 5% outage — 24× the base rate — and together they catch about a quarter of all new ≥ 5% outages.
  • The algorithm barely matters. Tuned XGBoost and LightGBM tie (264-run grid search). Up-weighting rare events hurt, and shallow trees generalized best to the next year.
  • Tree canopy is why I compare across models. With LightGBM alone, canopy looked important: removing it cost 12% (≥ 5%) and 22% (≥ 10%) of next-year PR-AUC. Repeating the same ablation with XGBoost, and with models trained only on new outages, the effect shrank to a few percent and sometimes reversed. From one model I would have called canopy a strong feature; across models it is weak and inconsistent. It is also correlated with rurality and the serving utility, so even where it helps, it is an association, not a cause.

How it's built

IngestPython scripts download outages, HRRR storm ingredients, storm reports, tree canopy rasters and Census tables.
Transformdbt on DuckDB: staging → intermediate → marts, 57 tests, a 3.5M-row modeling table.
ModelA YAML-driven benchmark suite: baselines, logistic, XGBoost, LightGBM; three splits; MLflow tracking.
ServeStreamlit dashboard on precomputed Parquet, packaged with Docker; CI on GitHub Actions.

Python, SQL, DuckDB, dbt, pixi, scikit-learn, XGBoost, LightGBM, MLflow, geopandas, rasterio, Streamlit, Plotly, Docker, GitHub Actions.

Data traps found along the way

  • EAGLE-I only records counties with outages, and sometimes the system itself was down. A national "heartbeat" — any county in the U.S. reporting — separates "no outages" from "no data".
  • St. Louis County's outages were filed under St. Louis City's code from mid-2020 to 2024; the two are modeled as one region.
  • The 2023 file renamed its outage column; early September 2025 recorded every snapshot twice.
  • The tree-canopy raster's "no data" value was 0 — a real value — which made farmland read as 45% forest until it was caught.
  • DuckDB's least(100, NULL) returns 100, which turned blank counts into "100% out"; a regression test now guards it.

Limitations

The weather is short-range, not a 24–48 hour forecast — the HRRR archive is close to observed weather, so the scores are an upper bound for planning a day ahead. The next-year split rests on one test year, there are no confidence intervals yet, and each county has a single weather point.
